The Harness · Chapter 3

Tools & Environment

The agent's hands are a design surface. Change the interface and the same model solves more problems; give it the wrong tools, or too many, and it solves fewer.

~10 MIN READ1 LIVE INSTRUMENT

Give GPT-4 Turbo a plain shell and point it at SWE-bench Lite: it resolves 11.0% of the issues. Keep the model and the tasks fixed, replace the shell with a purpose-built interface, and it resolves 18.0%. That is seven points, a 64% relative gain, and not one weight changed.1 This chapter is about that interface: the tools an agent holds, the machine it runs them on, and why both deserve as much engineering as the prompt.

The interface is a variable

The Princeton team behind SWE-agent named the thing they built an agent-computer interface, by deliberate analogy with the IDE. Humans got better at software when editors learned to jump to definitions and underline errors. Models are no different, except that their editor has to be designed for a reader that sees text, not pixels.1

Their four design principles read like a style guide for any tool you will ever hand a model: actions should be simple and easy to understand; they should be compact and efficient; feedback should be informative but concise; and guardrails should stop errors from compounding.1 None of these is about the model. All of them are about you.

What a good tool looks like

Anthropic's guidance on writing tools lands in the same place from the other direction.2 Consolidate: one schedule_event beats separate list_users, list_events and create_event calls, and search_logs beats read_logs. Namespace by service and resource, as in asana_projects_search, so similar tools stop colliding. Return high-signal context: a Slack tool answering in a concise format used 72 tokens where the detailed one used 206. Claude Code caps tool results at 25,000 tokens and nudges the agent toward narrower queries when it hits the cap. Prefer names to UUIDs, because agents handle natural-language identifiers far better than opaque ones.2

“Tools are a new kind of software reflecting a contract between deterministic systems and non-deterministic agents.”— Ken Aizawa, Anthropic (2025)

The cheapest lever is the description. Anthropic's platform docs call detailed descriptions “by far the most important factor in tool performance” and ask for at least three to four sentences per tool.3 Compare:

// before
get_stock_price  "Gets the stock price for a ticker."
  ticker: string

// after
get_stock_price  "Returns the most recent trade price, in USD,
  for one exchange-listed ticker. Use it when the user wants a
  current quote. It returns no history, volume or fundamentals;
  call a different tool for those. Fails on unlisted symbols."
  ticker: string   // uppercase symbol, e.g. "AAPL"

The SWE-agent ablations put numbers on these principles.1 A 100-line file viewer beat both a 30-line window and the whole file, which is pagination by another name. An editor that lints every change beat one that does not, which is a guardrail. Summarized search beat iterative search, which is high-signal returns. And iterative search scored below no search at all: a badly shaped tool costs more than a missing one. Try it.

Field noteReview tools like public APIs. Every tool gets a description of three or more sentences saying what it returns, when to use it and what it will not do. Default responses to a concise format, paginate anything that can grow, and if two tools are usually called back to back, merge them.

The tool-count cliff

More tools do not mean a more capable agent. Anthropic lists bloated tool sets with ambiguous decision points among the most common failure modes and recommends a minimal viable set.6 The measurements agree. With a large MCP tool pool dumped into the prompt, RAG-MCP found tool-selection accuracy of 13.62%; retrieving a shortlist first raised it to 43.13% and more than halved prompt tokens.7

A production routing study with 110 agents and 584 tools saw F1 on under-specified requests fall 16 to 23 points as the catalog grew from 10 agents to 110. Even with perfect retrieval the ceiling dropped about 10 points, a confusion gap that no shortlist can close; embedding shortlists won back 10 to 11 points.8 On edge devices, pruning the tool list improved function calling and cut execution time by up to 70% and power by up to 40%.9

Manus adds a constraint from the serving side: do not add or remove tools mid-task. Definitions sit near the front of the context, so changing them invalidates the KV cache and leaves earlier calls pointing at tools that no longer exist. Their fix is to keep the list stable and mask token logits instead. Mask, don't remove.10

MCP: the standard and its bill

The Model Context Protocol is JSON-RPC 2.0 over stateful connections with capability negotiation. Servers offer tools, resources and prompts; clients offer sampling, roots and elicitation. The spec takes the Language Server Protocol as its model, and the payoff is the same: write an integration once and every compliant client can use it.11

The bill arrives before the first question. The GitHub MCP server's 93 tools take roughly 55,000 tokens of definitions, loaded whether or not the task touches GitHub.4 That is over a quarter of a 200K window spent on a menu. Drag the slider above to see how fast a few servers add up.

Then there is the attack surface. The spec says it plainly: “Tools represent arbitrary code execution and must be treated with appropriate caution,” and descriptions from untrusted servers are untrusted input.11 Invariant Labs showed why. Hidden instructions in a tool description got Cursor to read ~/.cursor/mcp.json and ~/.ssh/id_rsa and leak them. A server can change its descriptions after you approve it, and a malicious tool can shadow the behavior of a trusted one on the same client.12

Two teams converged on the same answer. Anthropic proposed presenting MCP servers to the agent as a filesystem of code modules: the agent reads only the files it needs and writes code that calls them, so intermediate results stay in the execution environment and sensitive fields can be tokenized before the model sees them. One workflow dropped from 150,000 tokens to 2,000.5 Cloudflare turned MCP schemas into a TypeScript API and ran the generated code in V8 isolates that start in milliseconds, use a few megabytes, and can reach nothing but the bound servers.13

“LLMs are better at writing code to call MCP, than at calling MCP directly.”— Kenton Varda & Sunil Pai, Cloudflare (2025)

Code means a sandbox

Once the agent writes and runs code, isolation stops being optional. The question is how thick the wall needs to be, and the answer comes from two numbers: how much you trust the code, and how fast the environment must start.

The sandbox also changes what you can permit. Claude Code pairs permission allowlists with OS-level filesystem and network restrictions so the agent can work with fewer interruptions inside a known boundary.18 The wall is what makes autonomy affordable.

Once there's a disk, use it

A sandbox comes with a filesystem, and a filesystem is memory the context window cannot match. Anthropic recommends holding lightweight identifiers such as paths, stored queries and links, then loading the content just in time, because recall degrades as the window fills.6 Manus treats the file system as unlimited, persistent, structured memory and compresses only restorably: drop the page but keep the URL, drop the document but keep the path. The economics push hard in that direction. Their input-to-output ratio runs about 100:1, and cached input costs $0.30 per million tokens against $3 uncached.10

Skills apply the same idea to instructions. A skill is a folder with a SKILL.md: a YAML name and description, a body, and optional files. Only the name and description sit in the system prompt at startup; the body loads when the task matches; linked files load only when needed. Anthropic compares writing one to assembling an onboarding guide for a new hire.19 The always-loaded file, CLAUDE.md, should hold only what applies to every session. The docs are blunt about the alternative: “Bloated CLAUDE.md files cause Claude to ignore your actual instructions!”18

Deterministic edges, universal tool

Everything so far shapes what the model is likely to do. Hooks decide what must happen. In Claude Code they are shell commands, HTTP endpoints, MCP tools, prompts or subagents that fire on lifecycle events such as PreToolUse, PostToolUse and Stop. Exit 0 proceeds. Exit 2 blocks: a PreToolUse hook stops the call, a Stop hook keeps the agent working, and a PostToolUse hook can only report, because the tool already ran. JSON output can allow, deny or ask, inject context, or rewrite a tool's result.20 The docs draw the line cleanly: instructions in CLAUDE.md are advisory, while hooks “are deterministic and guarantee the action happens.”18

Field noteIf a rule must hold every time with zero exceptions (formatting, blocking writes to secrets, running the tests before stopping), it belongs in a hook, not a prompt. Use a Stop hook that exits 2 on a failing check as your quality gate.

The most general tool remains the shell. Claude Code's docs call CLI tools the most context-efficient way to reach external services and suggest teaching an unfamiliar one with --help. The harness composes the same way: cat error.log | claude -p "explain this error" makes the agent one more filter in a pipeline.18 A CLI call is also reproducible by a human, who can paste the exact command and get the same result.4

When no CLI or API exists, computer use is the fallback. Claude 3.5 Sonnet scored 14.9% on OSWorld from screenshots alone and 22.0% with more steps, against 7.8% for the next-best system, and Anthropic called the ability imperfect.21 Screenshots earn their keep as a checker even when text tools do the work: compare the rendered result against the target.18

Sandboxes, permission lists and hooks are where trust stops being a hope and becomes a mechanism. Chapter 4 takes that seriously: what to block, what to ask about, and how to let an agent act without letting it act on everything.
